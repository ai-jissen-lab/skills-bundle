# 頻度判定フロー・相乗り確認・棚卸し記録（テンプレート）

## 頻度判定フロー

新しい定期ジョブを作るとき、上から順に問う。

```text
1. これは「変化があったときだけ動けばよい」仕事か？
   → Yes：定期実行にしない。変化検知は軽い仕組み（プログラムの
     チェック）に任せ、エージェントの起動は変化があったときだけにする
   → No：2へ

2. 同じ対象を読んでいる既存ジョブがあるか？
   → Yes：新規に作らない。既存ジョブへ相乗りさせる（確認項目は次節）
   → No：3へ

3. 対象の変化速度はどれくらいか？
   - 日に何度も変わり、遅れると実害がある → 時間帯を絞ったうえで
     高頻度を検討する（理由を添えること）
   - 1日1回見れば足りる → 日次
   - 週単位でしか変わらない → 週次

4. 重い構築系（サイト構築、記事量産など）か？
   → Yes：定期化の前に、同日の並走本数が1〜2本に収まるか確認する。
     収まらなければ、既存の重いジョブと日を分ける

5. 頻度を決めたら、記録に残す。
   「ジョブ名／対象／頻度／頻度の根拠／報告する条件」を1行で書く。
   報告条件は「変化があったときだけ」が既定値
```

## 相乗り可否の確認

既存ジョブへ相乗りさせるときの確認。

- [ ] 既存ジョブが読んでいる対象と、新しい仕事の対象は同じか
- [ ] 既存ジョブの実行タイミングで、新しい仕事の鮮度は足りるか
      （日次ジョブへの相乗りで、日次で十分か）
- [ ] 既存ジョブの報告先と、新しい仕事の報告先は同じでよいか
- [ ] 相乗りで既存ジョブが重くなりすぎないか
      （読み取り量・処理量が大きく増える場合は分ける）
- [ ] 報告条件を分けられるか
      （片方だけ変化があったときに、その分だけ報告できるか）

「報告先」と「報告条件」が分かれすぎると、相乗りしても報告が二重・混線になる。その場合は、読み取りだけ相乗りして報告は分ける、という中間の形もある。大事なのは、作る前にこの5点を見て、形を決めてから実装すること。

## ジョブ棚卸しの記録の形

```markdown
定期ジョブ棚卸し（YYYY-MM-DD）
- 合計実行回数（平日1日あたり）：◯回
- 内訳：ブリーフィング系 ◯／検知・監視系 ◯／公開・更新系 ◯／その他 ◯
- 今回止めたもの：［ジョブ名］（理由： ）
- 今回頻度を落としたもの：［ジョブ名］ ◯→◯（理由： ）
- 相乗りに変えたもの：［新しい仕事］→［既存ジョブ名］
```

合計回数を実測するのが先で、個別の議論はその後。停止したジョブには、止めた理由を必ず付ける。
