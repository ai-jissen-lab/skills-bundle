# memory-metabolism（記憶の代謝）

AIアシスタントが「最近バカになった」「前に直したはずの間違いを繰り返す」「言ったことと違う答えが返る」とき、原因はモデルの劣化ではなく、メモリファイルの育ちすぎと自己矛盾であることが多い。常駐メモリ（毎回読み込まれるファイル）が肥大すると、古い決定と新しい決定、終わった案件と進行中の案件、訂正されたはずの事実と訂正前の記述が同居し、アシスタントはその中から間違った方を拾う。

このスキルは、メモリを「足し続けるもの」から「代謝させるもの」に変えるためのルール。肝は3つだけ。

1. **常駐は「毎回必要な前提」だけ**。案件・日次・経過は別の置き場へ逃がす
2. **チェックは頻繁に、消すのは承認制でまとめて**。見つけたその場で勝手に消さない
3. **整理の前後で、過去の訂正を再検証する**。短くなったこと自体を成果にしない

対象はファイルベースのメモリを持つAIアシスタント全般（ClaudeのMEMORY.md／CLAUDE.md／AGENTS.md、各種エージェントのメモリファイルなど）。ファイル名が違う環境では、設定ファイル（`config.md`）で読み替える。

## 設定（最初に確かめる）

作り始める前に、設定がもう決まっているかを確かめる。見る順番は、今回の依頼の中の指定、このスキルのフォルダにある`config.md`、プロジェクトの指示やメモリにある設定。どこかで決まっていれば、それに従ってすぐ始める。

どこにも設定がないときは、始める前に一度だけ尋ねる。今の既定値を先に見せて、変えたいところだけ答えてもらう。尋ねるのは次の5項目まで。

| 項目 | 既定値 | 尋ねること |
|---|---|---|
| 常駐ファイル | MEMORY.mdとAGENTS.md（環境によりCLAUDE.md等） | 毎回読み込まれているファイルはどれか |
| 置き場の構成 | 常駐／シーン別／日次ログ／アーカイブの4層 | シーン別フォルダや日次ログの置き場所 |
| 常駐の上限の目安 | 合計30,000字（後述「サイズの目安」） | チームや個人で決めた上限があるか |
| チェックの頻度 | 読み取り専用チェックはタスク開始時、適用は週1回まとめて | 定期実行に載せるか、手動のままか |
| 承認者 | メモリの持ち主本人 | 整理の適用を誰が承認するか |

- 「全部このままでいい」と一言で答えられる聞き方にする
- 答えは保存して次から尋ねないことを、質問の最後に一言添える
- 決まった設定は、このスキルのフォルダに`config.md`として保存する。形は`config.example.md`と同じにする。ファイルを書けない環境では、`config.md`の中身をメッセージで渡し、プロジェクトの指示に貼るよう案内する

## 置き場の4層（分類の型）

メモリの置き場は4層に分ける。新しい情報を覚えるときも、棚卸しで行き先を決めるときも、この表で判断する。

| 層 | 置くもの | 置かないもの | 例 |
|---|---|---|---|
| **常駐** | 毎回必要な前提だけ。持ち主の基本情報、承認ルール、絶対に外せない約束、他層への目次 | 案件の経過、日付のある予定、実測値、長い経緯 | 「承認はメール送信のみ」「報告は結論先行で」 |
| **シーン別** | 場面ごとの詳細。仕事の進め方、事業・案件、分野別のルールと履歴 | 全場面に共通する前提（それは常駐） | 仕事の進め方.md、案件.md、分野別.md |
| **日次ログ** | その日に起きたことの記録。判断の経過、試したこと、失敗 | 整理された結論（それはシーン別か常駐へ昇格させる） | 2026-01-15.md |
| **アーカイブ** | 終わった案件、置き換え済みで古くなった記述、整理前のバックアップ | 現役の情報 | 終了したプロジェクトの記録一式 |

判断の型：

- **毎回読みたいか？** そうでなければ常駐に置かない
- **場面が決まっているか？** 決まっているならシーン別。タスク開始時に、目次を見て該当シーンだけ読む運用とセットにする
- **日付に紐づく経過か？** そうなら日次ログ。結論だけ後で上の層へ昇格させる
- **終わったか、置き換えられたか？** そうならアーカイブ。消すのではなく移す

常駐ファイルの形は「超重要事項＋シーン別ファイルへの目次」を基本形とする（テンプレートは`templates/MEMORY.template.md`）。目次には、各シーン別ファイルについて「いつ読むか」と「何が入っているか」を1行ずつ書く。目次がない分割は、ただの散らかりになる。

## 常駐に足す前の3問

常駐ファイルに1行足す前に、必ずこの3問を問う。1つでも外れたら、足す先を変える。

1. **これは「毎回必要な前提」か？** 特定の案件・日付・場面の話なら、シーン別か日次ログへ
2. **実測値や時点の数字ではないか？** 測定した数値（件数、金額、サイズ、達成率）はすぐ古くなる。常駐には置かず、測った時点の日次ログか棚卸しファイルへ
3. **既にある記述と矛盾しないか？** 矛盾するなら、足すのではなく「置き換え」として扱い、古い方をアーカイブへ移す。両方を残さない

逆に、シーン別や日次ログに書くときはこの3問は要らない。詳細はそちらに遠慮なく書く。常駐だけを痩せさせるのがこのスキルの仕事で、記録そのものを減らすことではない。

## サイズの目安

文字数は健康の目安であって、目的ではない。短くすること自体を成果にしない。ただし、測らなければ育ちすぎに気づけないので、棚卸しのたびに実測する。

| 常駐の合計 | 状態 | 動き |
|---|---|---|
| 30,000字まで | 健全圏 | 通常運用。足す前の3問だけ守る |
| 30,000〜50,000字 | 警戒圏 | 棚卸しをして、シーン別へ逃がせるものを候補に出す |
| 50,000字超 | 危険圏 | 育ちすぎ。矛盾・重複が混ざっている前提で棚卸しを優先する |

根拠は実測の事例から。ある運用では、常駐の合計が約65,000字（MEMORY.mdだけで47,451字・86項目）に達した時点で、訂正済みの事実と古い記述の矛盾が目立ち始めた。整理後はMEMORY.mdを12,066字（超重要事項＋目次）まで圧縮し、詳細は9つのシーン別ファイル（合計約79,000字）へ**要約せず全文のまま**移した。情報量は減らしていない。毎回読む量だけを減らした。

- 項目数も併せて測る。1ファイル100項目を超えたら、内容以前に分割を検討する
- サイズは棚卸しのたびに測り直し、日次ログに残す。常駐ファイルの中に「現在のサイズ」を書かない（書いた瞬間に古くなる）

## 棚卸しの手順（5ステップ）

整理はこの順番で進める。途中のステップを飛ばさない。

### 1. 測る

常駐ファイルすべての文字数と項目数を実測し、前回と比べる。測っていないファイルは「未測定」と書く。推測で埋めない。

### 2. 候補を出す（読み取り専用）

次の4観点で候補を拾い、候補リストにまとめる（型は`templates/inventory-candidates.template.md`）。この段階では**ファイルを変更しない**。

| 観点 | 見ること | 候補の例 |
|---|---|---|
| サイズ | 大きい項目、1項目が長い記述 | シーン別へ移せる長い経緯 |
| 期限切れ | 日付が過ぎた予定、終わった案件、失効した条件 | 完了したイベントの準備メモ |
| 重複 | 同じ内容が常駐とシーン別、日次ログに二重にある | 振り返り文書と常駐の重なり |
| 矛盾 | 新旧の決定が両方残っている | 変更前の手順と変更後の手順の同居 |

### 3. 分類する

候補1件ごとに行き先を決める：残す／シーン別へ移す／アーカイブへ移す／（承認されれば）消す。移す場合は**全文移設が原則**で、要約して原文を捨てない。要約は情報の欠落であり、欠落は後の誤答の種になる。

### 4. 承認を得る

候補リストを持ち主（承認者）に見せ、承認された分だけを適用する。承認されていない候補には手を付けない。「ついでに」他の候補を一緒に適用しない。

### 5. 適用して検証する

適用前にバックアップを取り（後述）、承認分を適用し、最後に訂正検証（後述）を通してから完了とする。検証が崩れたら、その整理は完了と言わず、バックアップから戻して原因を調べる。

## チェックと適用の頻度

- **チェックは頻繁に**：読み取り専用のチェック（測る＋候補を出す）は軽い。タスクの開始時や、定期実行に載せられる環境なら毎晩でもよい。候補があるときだけ報告し、「変化なし」の報告のためだけに持ち主の注意を引かない
- **適用はまとめて**：消す・移すの適用は週1回程度にまとめ、承認も1回で済ませる。見つけるたびに1件ずつ聞かない
- 定期実行に載せる場合も、自動で編集する仕組みにはしない。自動なのは「候補を拾うところ」までで、適用はいつも承認の後

## 訂正台帳（守るべきものの型）

過去に持ち主が訂正した事実（誤答→修正された論点）は、整理のときに一番消してはいけないもの。訂正は「その話題では前に間違えた」という警告であり、消えると同じ間違いが戻ってくる。

- 訂正された論点は台帳に別に残す（型は`templates/corrections.template.md`）。台帳の項目は、サイズが大きくても削除・移設の候補から外す
- 台帳には、論点、訂正前の答え、訂正後の答え、訂正された日付を書く。訂正前の答えを残すのは、間違いを再発させないためであり、現行の答えと混同しないよう「旧（誤）」と明記する

### 整理の前後の検証

整理の前と後に、台帳から最低3問を選んで実際にアシスタントへ質問し、答えが訂正後の内容と一致するか確かめる。

- 適用前：今の答えを記録する（これが崩れていないかの基準になる）
- 適用後：同じ質問をもう一度し、答えが変わっていないか比べる
- 1問でも崩れたら、その整理は失敗として扱う。バックアップから戻し、何が消えたか・移ったかを調べてから、直して再検証する
- 「短くなった」「速くなった」は完了の条件ではない。**答えが崩れていないこと**が完了の条件

## バックアップ

- 整理を適用する前に、常駐ファイル一式のコピーを日付付きで残す（例：`memory-backup-YYYY-MM-DD/`）。非公開のGitリポジトリで版管理できればなお良い
- バックアップはアーカイブ層に置き、常駐には混ぜない
- 消しすぎた・移しすぎたと分かったら、まずバックアップから戻す。戻せる前提があるから、承認制の整理を前に進められる

## やらないこと

- 見つけたその場で、承認なく消す・直す
- 短くなったこと自体を成果として報告する
- 移設のときに要約して原文を捨てる
- 実測値（件数・金額・サイズ）を常駐に固定する
- 訂正台帳の項目を「古いから」と候補に入れる
- チェックのたびに「変化なし」を報告して持ち主の注意を消費する
- 層を増やしすぎる。4層で足りないときは、層ではなくシーン別ファイルの分け方を見直す

## 最終チェック

- [ ] 設定（config）を確かめ、なかったときは既定値を見せて尋ね、答えを残した
- [ ] 常駐の合計サイズと項目数を実測した（推測で埋めていない）
- [ ] 候補を4観点（サイズ・期限切れ・重複・矛盾）で出し、ファイルはまだ変更していない
- [ ] 候補ごとに行き先（残す／移す／アーカイブ／消す）を付け、移設は全文が原則になっている
- [ ] 訂正台帳の項目が候補から外れている
- [ ] 承認された分だけを適用した
- [ ] 適用前にバックアップを取った
- [ ] 適用の前後で台帳から最低3問を再質問し、答えが崩れていないことを確かめた
- [ ] 崩れた場合は戻して直し、再検証を通した
