# draft-or-done（完了か、下書きか）

AIアシスタントは「買いました」「送りました」「公開しました」を、画面の雰囲気で言いがちだ。品物も金額も宛先も正しく画面に並んでいる。カートに入っている。下書きは保存されている。デプロイはReadyと出ている。どれも完了ではない。

失敗のパターンは決まっている。**中間状態を、完了と取り違える**こと。そして一度「完了」と報告されると、その前提で集計が動いたり、次の作業が始まったりして、間違いが広がる。逆向きもある。「送信に失敗した」と報告されたものが、実は送信済みだった、という取り違えだ。

このスキルは、完了を「言い方」ではなく「証拠」で決めるためのルール。対象はコードのテスト検証ではなく、買い物・送信・予約・投稿・保存・公開といった日々の取引状態。肝は3つ。

1. **中間状態は完了ではない**。最終確認の手前は、どれだけ画面が整っていても未完了
2. **完了には証拠が1つ要る**。確定番号、履歴への出現、公開URLでの表示、読み戻し。証拠を示せない完了は言わない
3. **報告が食い違ったら、証拠に戻る**。新しい報告を採用せず、証拠そのものを確認する

## 設定（最初に確かめる）

このスキルには、使うサービスごとに「何が完了の証拠か」を定義する差し替えファイルがある。見る順番は、今回の依頼の中の指定、このスキルのフォルダにある`proofs.md`、プロジェクトの指示やメモリにある定義。

どこにも定義がないときは、組み込みの「証拠の型カタログ」（後述）で判断してよい。ただし、同じサービスを繰り返し使うなら、最初に一度だけ、そのサービスの証拠を定義して`proofs.md`に残すよう提案する。形は`proofs.example.md`と同じ。尋ねる場合も、定義が要るサービスだけに絞り、まとめて1回で聞く。

## 状態の階段（まず階段を描く）

報告の前に、そのサービスにどんな状態があるかを階段として並べる。階段を描かずに完了を言わない。

- 買い物：カート → 注文手続き → 注文確定 → 支払い完了 → 発送 → 配達
- 送信：下書き → 送信処理 → 送信済み（相手に届いたかは別）
- 予約：空き確認 → 仮押さえ → 予約確定 → 支払い
- 投稿：下書き → 予約投稿 → 公開
- 保存：編集中 → アップロード／保存中 → 保存完了
- デプロイ：ビルド成功 → デプロイ完了（Ready） → 本番反映
- 申込・発注：見積 → 申込送信 → 受付 → 確定 → 支払い完了

自分が今どの段にいるかを名指してから動く。「手続きをした」と「確定した」は別の段だ。

## 証拠の型カタログ

分野ごとに、「完了の証拠になるもの」と「証拠にならないもの」を決めてある。サービスが違っても、型はだいたいこの表に当てはまる。

| 分野 | 完了の証拠（これを見て言う） | 証拠にならないもの（これだけでは言わない） |
|---|---|---|
| 買い物・注文 | 注文番号と、注文履歴にその注文が現れていること | カートの画面、注文ボタンを押したこと、金額と宛先が正しく表示されていること |
| 送信（メール・メッセージ） | 送信済みフォルダやスレッドに現れていること、相手からの返信 | 下書きが保存されていること、送信ボタンを押した感覚、エラーが出なかったこと |
| 予約 | 予約番号と、予約一覧に現れていること | 空き表示、自分のカレンダーへのメモ、申込フォームの送信完了画面だけ |
| 投稿（SNS・記事） | 公開URLで、ログインしていない状態でも実際に見えること | 予約投稿の一覧に入ったこと、下書きのプレビュー、投稿ボタンの反応 |
| 保存・アップロード | もう一度開いて読み戻せること、更新日時や容量が変わっていること | 進捗バーの表示（97%など）、保存ボタンを押したこと、「保存しました」の一瞬の表示 |
| デプロイ・公開（Web） | 本番URLで、実際の表示が変わっていることを確認すること | ビルド成功、デプロイのReady表示、リポジトリにファイルがあること |
| 申込・発注・支払い | 受付番号や確定書面、決済履歴に現れていること | フォームの送信完了画面だけ、見積を送ったこと、請求書が発行されたこと（支払いとは別） |

### 証拠の強さ

証拠には強さがある。強い証拠が1つあれば完了と言える。弱いものしかないときは、完了と言わず「未確認」と報告する。

| 強さ | 例 | 扱い |
|---|---|---|
| 強い | 確定番号、履歴への出現、公開URLでの表示、読み戻し成功 | 完了と言える。番号やURLを報告に添える |
| 中くらい | 完了画面、確認メール | 可能なら強い証拠で裏を取る。裏が取れない間は「完了画面までは確認」と段を名指す |
| 弱い | ボタンを押した、進捗表示、エラーが出なかった | 完了の根拠にしない |

## 報告の型（状態＋証拠＋残り）

完了に限らず、状態の報告は3点セットでする。「done」「完了しました」の一言で終わらせない。

1. **状態**：階段のどの段にいるか（例：注文確定、ただし未発送）
2. **証拠**：何で確かめたか（例：注文番号 ○○、注文履歴で確認）
3. **残り**：まだ完了していない部分（例：支払いは未完了、配達は明日以降）

良い例：「注文は確定しています。注文番号は○○で、注文履歴に残っているのを確認しました。発送はまだです」
悪い例：「購入しました」「送っておきました」「公開済みです」

準備の報告も価値がある。ただし準備は準備と名指す。「カートに3点入れました。注文はまだ確定していません」は良い報告で、「買いました」は誤報だ。

## 集計や台帳を動かすとき

売上、件数、進捗などの集計は、誤報が一番広がる場所だ。

- 集計の数字は、証拠で読み戻してから動かす。報告を受けただけでは動かさない
- 集計を動かす場所は1つに決める（単一の正本）。別のチャットや担当は、正本を指すだけにして、独自の完了カウントを持たない
- 動かした後は、正本を読み戻して、数字が合っているか確かめる

## 締切と二重実行

- **締切は確定状態とセットで見る**。カートや下書きのまま締切を過ぎたものは「買っていない／送っていない」ものであり、もう実行できないことがある。報告ではその可能性まで言う
- **二重実行のリスクを警告する**。別のチャット、別の端末、別の担当のところに、未確定のカートや下書きや予約投稿が残っていると、誰かがそれを確定して二重になる。「あちらは確定しないでください」と分かる形で明示する
- 不可逆な操作（送信、発注、決済、公開）を繰り返す前に、前回の試みが実際には成功していないか、証拠側で確かめる。失敗の報告だけを根拠に再実行しない

## 報告が食い違ったとき

2つのチャット、端末、担当の報告が食い違ったら、新しい方を採用して進めない。

1. 止まる
2. 証拠そのもの（履歴、送信済みフォルダ、公開URLなど）を確認する
3. 証拠が示す状態を正とする
4. 先の報告が間違っていたら、平易な言葉で訂正する。実際に達していた状態と、達していなかった状態を、両方名指す（例：「送信済みと報告しましたが、実際は下書き保存までで、送信はされていませんでした」）
5. その前提で動いた集計や後続作業があれば、そちらも直す

自分が証拠に届かないとき（権限がない、履歴が見られない）は、推測で埋めず「未確認」と報告し、持ち主に証拠そのものの確認を頼む。確認が返るまで、その件は未確認のまま扱う。

## やらないこと

- 画面に正しく並んでいることを根拠に、完了と言う
- 進捗バーや一瞬の完了表示を根拠に、保存・送信の完了と言う
- ビルド成功やReady表示を根拠に、本番反映と言う
- 失敗の報告だけを根拠に、不可逆な操作をもう一度実行する
- 食い違った報告のうち、新しい方を証拠なしに採用する
- 集計を、読み戻しなしに動かす
- 「完了しました」の一言で報告を終わらせる

- [ ] 強い証拠を1つ確認し、番号・URL・履歴などの形で報告に添えた
- [ ] 報告が「状態＋証拠＋残り」の3点セットになっている
