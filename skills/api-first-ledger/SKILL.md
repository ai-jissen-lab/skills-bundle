# api-first-ledger（API優先と台帳）

AIエージェントに作業をさせると、ブラウザを開いて画面を操作する手順になりがちだ。画面操作は目に見えて分かりやすい反面、遅く、壊れやすい。画面の構成が少し変わるだけで止まるし、読み込み待ちに時間を使う。同じことがAPI（プログラムから直接データをやり取りする窓口）でできるなら、速く、安定して、再現性もある。

このスキルは「APIでできる仕事はAPIを先に探す」順序と、その判断材料である「API台帳」を維持するためのルール。肝は3つ。

1. **作業前に、必要な能力を特定して台帳を引く**。台帳にあるAPIで処理できる作業は、ブラウザ操作・手作業・AIの推論よりAPIを優先する
2. **台帳に取り込むのは、完全無料で継続性が高いものだけ**。除外条件に1つでも当てはまれば取り込まない
3. **台帳は接続状態を含む生きた文書として維持する**。新しいAPIを接続・承認したら、その場で更新する

## 使う場面

- 作業に入る前に、進め方（APIか、ブラウザ操作か、手作業か）を決めるとき
- 新しいAPIを見つけて、台帳に加えるか判断するとき
- APIが失敗したときのフォールバックを決めるとき

## API台帳とは

使えるAPIを一覧にしておく台帳。記録するのは名前だけではない。

- 何ができるか（能力の単位で書く。「○○の検索」「○○の取得」など、仕事の言葉で）
- 接続の状態（接続済みか、キーが要るか、キー不要か）
- 無料枠の条件（上限と、超えたときに止まるのか課金されるのか）
- 商用利用の可否と、条件を確認した日

1件の記録の形は `templates/ledger-entry.template.md` を使う。作業に入る前にこの台帳を見て「この仕事はあのAPIでできる」と判断できれば、APIを優先する。

利用者（人）にはAPI名を覚えさせない。人は「○○を調べて」と普通の言葉で頼むだけにし、どのAPIを使うかは台帳を見てAI側が判断する。覚えさせる仕組みは、使われなくなる。

## 優先順位

同じ能力を持つAPIが複数あるときは、この順で選ぶ。

**無料 ＞ 高速 ＞ 高精度**

運用は継続するものなので、まず費用がかからないことが土台になる。その上で、繰り返し実行する仕事では速度が効く。精度は、無料と速度で足りない場面だけ求める。場面ごとに悩まず、順序で決めるためのルールだ。

## 失敗したら、記録してからフォールバック

APIが失敗したら、まず理由を記録する。そのうえで、ブラウザ操作や手作業にフォールバック（代替手段へ切り替える）する。

理由を記録しないと、次回も同じAPIで同じ失敗を繰り返す。逆に、失敗の理由が残っていれば「このAPIはこの条件では使えない」という台帳側の知識になる。優先順位のルールと、失敗の記録はセットだ。

## 採用の考え方：コストゼロから始める

企画と採用の出発点は固定する。常に「コストがかからない形で、ニッチトップを狙えるモデル」から考える。そして台帳に取り込むのは、完全無料で継続性が高いものだけ。

コストゼロは節約の美学ではない。お金で解決する形は誰でも真似できるが、コストがかからない形で狭い領域の一番を取る形は真似されにくく、売上ゼロの期間でも潰れない。

世の中の「無料で使えるAPI」は一様ではない。最初だけ無料クレジットが付いて尽きたら従量課金になるもの、無料に見えて登録にクレジットカードが必須のもの、無料枠はあるが商用利用は対象外のもの、無料プランの終了・改定が予告されているもの。こういうものを運用の部品にすると、ある日突然、費用が発生したり、止まったり、条件違反になったりする。

## 除外条件5つ（取り込まないもの）

採用の判定は「当てはまったら取り込まない」で運用する。グレーなら取り込まない側に倒す。

1. **従量課金のみのもの**：料金ページに単価表しかなく、無料枠の記載がないもの。無料枠があっても、超過分が自動で従量課金になる設計のものは実質これに近い。自律運用では実行回数が読みにくいので、入口で外す
2. **初回クレジットだけが無料のもの**：「登録時に○○円分のクレジット進呈」型。尽きた先は従量課金だ。判定は「クレジットが尽きた後も無料か」で行う
3. **カード必須のトライアル**：無料期間でもクレジットカード登録が必須のもの。カードを登録した時点で、それは「解約を忘れたら課金される仕組み」に乗っている。無料の部品としては数えない。本当に必要なら、無料ではなく有料の採用として別途判断する
4. **終了・改定が見えているもの**：無料プランの終了予告、料金改定の告知、買収やサービス統合の発表が出ているもの。採用済みのものに告知が出たら、代替を先に探す
5. **法人の商用利用が無料枠の対象外のもの**：利用規約で、無料枠が個人利用や非商用に限られているもの。価格の問題ではなく条件の問題なので、どれだけ便利でも取り込まない。「商用利用」の定義はサービスごとに違うため、料金ページではなく規約側で確認する

## 採用までの確認手順

1. 候補を見つけたら、料金ページと利用規約を確認する（無料枠の有無と上限／超過時の扱い／商用利用の可否は規約側で）
2. 除外条件5つに当てる。1つでも当てはまれば取り込まない。理由を記録して終了
3. 継続性を見る（終了・改定の告知がないか／提供元の体制は公式か、個人の実験的公開か）
4. 台帳に記録する（`templates/ledger-entry.template.md` の形で、確認日つき）
5. 実際に接続して、想定どおり無料で動くか確認する。想定と違えば、台帳の記録を直すか、採用を取りやめる

チェックは `templates/adoption-checklist.template.md` を使う。

## 台帳の維持

- 台帳は接続状態を含む「生きた文書」として維持する。新しいAPIを接続したら、その場で更新する
- 無料の条件は変わるものだ。条件が変わったことに気づいたら、その場で台帳を直す
- 失敗した理由の記録は、台帳の該当APIの備考に残す

## やらないこと

- 台帳を確認せずに、ブラウザ操作から作業を始める
- 除外条件に当てはまるAPIを「とりあえず」で取り込む
- 無料枠の上限だけ記録して、超過時の扱い（自動課金か、停止か）を書かない
- 確認日を付けずに条件を記録する
- 利用者にAPI名や接続状態を覚えさせる
- APIの失敗理由を記録せずにフォールバックする
