# email-thread-ops（メール・スレッド読みと下書き）

メール返信の下書きが「文章としては整っているのに、どこか噛み合わない」原因の多くは、文章力ではない。読んでいる範囲の狭さだ。相手の最新メールだけを見て書くと、前に決まったこと、まだ決まっていないこと、別の経路で対応済みのことが文面から落ちる。落ちた分は、受け取った相手には「話を聞いていない」ように見える。

下書きで失敗するのは、文面を書いている段ではない。その前の確認を飛ばしたときに起きる。書き直しのコストより、確認を飛ばしたことの手戻りのほうが大きい。

このスキルは、メール返信の標準を「書く前の確認」と「文面の型」に固定するためのルール。肝は3つ。

1. **下書きの前に、スレッド全体を原文で読む**。要約や件名だけで判断しない
2. **書く前に、確認項目をチェックリストで通す**。特に「相手が求めていることと、まだ決まっていないことを分ける」「数字と条件の整合」「すでに他で対応済みでないか」
3. **文面は固定した型で組み、送信は別の段として扱う**。送信は承認を得てから。確認は送信済みフォルダで

## 使う場面

- メール返信の下書きを作るとき
- AIに下書きを作らせる際の指示に、確認項目を含めるとき
- 下書きができたあと、送信前の確認をするとき

## 読む範囲（「全体」とはどこまでか）

下書きの前に読む範囲は、相手の最新メールだけではない。

- 相手の最新メール（当然、原文で）
- 自分が過去に送ったメール（何を約束し、何を提案したか）
- 過去の経緯（条件や日程がどう変わってきたか）
- 添付ファイル（見積や資料の中身が、本文の前提になっていることが多い）
- まだ決まっていないこと（未決事項。返信で触れるべきか、保留すべきかの判断材料）

要約は便利だが、要約を作った側の解釈が混ざる。言い回しの温度や、相手が何に困っているかといった機微は、原文にしか残っていないことがある。下書きの質は、だいたいこの読み込みの深さで決まる。

## 下書き前チェックリスト

書き始める前に、`templates/pre-draft-checklist.template.md` を上から順に確認する。1つでも埋まらない項目があれば、書く前にそちらを先に片づける。特に効くのは次の3つ。

- **求めていることと未決事項を分ける**：書く前に分けて書き出す。求められていることには答えを書く。決まっていないことは、決まったふりをせず「未定である」こと自体を文面に入れる。この区別をせずに書くと、未決事項まで確定したような文面になり、あとで食い違う
- **数字と条件の整合**：見積・請求・人数・日程・支払条件のような、間違えると実害が出る部分の照合。本文と添付で人数が違う、前に送った見積と金額がずれている、という取り違えは、書く段ではなく確認の段でしか防げない
- **他で対応済みでないか**：電話や別のツールで話が進んでいるのに知らずに返信を書くと、二重の回答になる。読み込みの中で「この件はもう動いている」ことに気づければ、下書き自体を作らずに済む。書かない判断も、下書きの仕事のうちだ

## 文面の型

文面の組み立ては固定する（ひな形は `templates/message-structure.template.md`）。

1. **冒頭**：お礼とクッション言葉。連絡へのお礼、前回のやり取りへの一言など、本文に入る前の短い助走
2. **本題**：相手が求めていることへの答えから入る。結論を先に置く
3. **未決事項**：決まっていないことは、決まっていないと明示する。見通しがあるなら、その旨を添える
4. **結び**：確認や返信を求める場合は、その一言。なければ短い挨拶で閉じる
5. **署名**：会社名の次行に名字。形は統一する

口調の決まりも型に入れる。

- 自然で丁寧な敬語にする。過剰な敬語や、不自然な営業表現、持ち上げすぎる言い回しは避ける
- 断定的・ぶっきらぼうな言い回しにしない。かといって、馴れ馴れしくもしない
- 過去のやり取り・関係性・相手の立場・商談の進み具合に合わせる。初めての相手への文面と、継続中の相手への文面は同じにしない

過剰な敬語は、丁寧さではなく距離として伝わることがある。逆に、関係ができている相手に急に堅い文面を送るのも不自然だ。スレッド全体を読んでいるからこそ、その相手との「いつもの温度」で書ける。

署名の形も統一する。会社名を置き、その次の行に名字だけを置く形。部署名や肩書を足したり引いたりすると、同じ相手に違う顔で届く。統一されていること自体が「いつもの相手」として認識される材料になる。

## 送信の段

下書きができても、送信は別の段である。

- 送信は承認ゲートに残す。文面を持ち主に見せて、承認を得てから送る。送った文面は取り消せないので、ここだけは止める、という設計
- 送信したかどうかは、送信済みフォルダに自分の送信が現れていることで確認する。下書きが保存されていることや、エラーが出なかったことは、送信の証拠にはならない

## やらないこと

- 要約や件名だけを見て下書きを書き始める
- 添付ファイルを開かずに本文だけで判断する
- 未決事項を、決まったことのように書く
- 数字と条件の整合を確認せずに文面の推敲から入る
- 対応済みの件に、もう一度返信を書く
- 承認なしに送信する

## 最終チェック

- [ ] スレッド全体を原文で読んだ（最新メール・送信済み・経緯・添付・未決事項）
- [ ] 相手が求めていることと、まだ決まっていないことを分けて書き出した
- [ ] 見積・請求・人数・日程・支払条件など、数字と条件の整合を確認した
- [ ] すでに他で対応済みでないか確認した
- [ ] 宛先が合っているか確認した（返信先、Ccの要否）
- [ ] 文面は型（冒頭→本題→未決事項→結び→署名）で組み、口調は相手との温度に合わせた
- [ ] 送信は承認を得てから行い、送信済みフォルダで確認した
